## 2. サブセット(4 種)とリーク率

抽出方式の違いがリーク率(サブセット外へのリンク割合)に直結することを確認:

| サブセット | 方式 | ノード | 内部エッジ(有向) | 外部へ(out) | 外部から(in) | **leak_out** |
|---|---|---|---|---|---|---|
| idwin_late_10k | ページID末尾 1 万 | 10,000 | 28,229 | 554,316 | 207,723 | **95.2%** |
| bfs_geo_30k | 地理系 12 種記事から out-link BFS(cap40, ≤3hop, in次数>1万を除外) | 30,000 | 1,662,557 | 5,905,734 | 14,617,961 | 78.0% |
| bfs_mixed_30k | 混合理系/文化系 10 種記事から同 BFS | 30,000 | 1,376,803 | 4,829,817 | 11,854,813 | 77.8% |
| bfs_geo_100k | 地理系 BFS(cap60, ≤4hop) | 100,000 | 6,874,293 | 13,286,361 | 26,024,757 | **65.9%** |

- **ID 窓抽出はコミュニティ評価に使用不能**(内部構造がほぼ無い: 後述 crossF=0.002)。§7.1 の注意が定量的に実証された。
- BFS でも 30k では約 78% がサブセット外へ。**サブセットは「グラフの切り身」でありコミュニティの合併体ではない**ため、リーク自体は分割の失敗を意味しない(§7.1 方針通り、独立性評価は内部エッジで行い、リークは別建てで報告)。
- **規模を上げるとリーク率は低下**(78%→66%)。境界効果の縮小 = 全体グラフではさらに改善が見込める。

### 3.4 ハブ抑制手法の比較(最重要の手法知見)

| 手法 | 結果 |
|---|---|
| hub ノード削除(in次数>1k/3k を落とす) | **グラフ破砕**(コミュニティ中央値=1)。スター型銀河(Stub↔地域ハブ)のスポークが切れる |
| 次数予算 both モード(両端 rank<B のみ保持) | **同様に破砕**(30k: 29%保持で中央値1、100k: 33%保持で中央値1) |
| **smart モード**(低次数ノードの辺は常時保持、高次数↔高次数のみ間引き) | **構造を保持**(69%/63.5% 保持、中央値 549/1,474)。銀河内部は温存し「銀河間高速道路」のみ剪定 |
| エッジ重み 1/(log d_u・log d_v) | ほぼ無効果(重みレンジが 2.4 倍しかない) |
| エッジ重み 1/(d_u・d_v) | **悪化**(cross_frac 0.38–0.51)。ハブ辺は本物のコミュニティシグナルも運ぶ |

### 3.5 境界ノード

- boundary_node_ratio(1 本でも社区間エッジを持つノード割合): geo100k p50=**0.984**、mixed p50=0.827、boundary_any(サブセット外リンク含む)= **ほぼ 100%**。
- 平均次数 69–94 の稠密グラフでは「境界を全く持たない銀河」は存在しない。**§4.3 の設計(境界はアンカー/集約重みで扱い、クロスリンク全量をローカルジョブに持たせない)が必須**であることの定量根拠。
- ただし容量の観点: 境界「エッジ数」比率(out_ratio)は 0.24–0.42(100k, res0.5–1.0)であり、境界情報は「コミュニティあたり隣接コミュニティ要約 + 代表アンカー点」に圧縮可能(隣接コミュニティ数は top ペア構造から見て各コミュニティ数十程度)。

### 3.6 階層化(L2)

- mixed 30k(L1=res2.0 で 27 コミュニティ → L2 Leiden):**4 実クラスタ + 1 孤立**。out_ratio2 = 0.222 / 0.292 / 0.424 / **0.051**(小クラスタ)。L1 の out_ratio p50=0.532 から **L2 で 0.22–0.29 へ大幅低下** → 上位にまとめるほど独立性が上がる=階層化は機能する。
- geo 30k: L2=4 クラスタ、out_ratio2 0.36–0.49(L1 0.63 から改善するが高い)。
- geo 100k raw res0.5: L1 が既に粗すぎて L2 退化(1 クラスタ)。**階層評価は「細かい L1(res≥2)→ L2 集約」の順で行うべき**。

## 4. §13 合格ラインとの照合

### 肯定的サイン(観測されたもの)
- ✅ 数百〜数千ノードのコミュニティが多数(res1–2 でサイズ中央値 549–2,136、p25–p75 が 288–16,412)
- ✅ 最大コミュニティのシェアが極端でない(res≥1.0 で 8.6–15.1%。res0.5 では 30–51% になることがある → resolution 選択の問題)
- ✅ modularity 0.51–0.65(強い構造)
- ✅ コミュニティの意味的一貫性(テーマ・カテゴリと良好に対応)
- ✅ **規模拡大で外部結合率が低下**(geo: oR p50 0.63@30k → 0.37@100k、leak 78%→66%)。全グラフではさらに改善する方向性
- ✅ 上位クラスタ化で out_ratio が低下(mixed: 0.53 → 0.22–0.29)
- ✅ 社区間エッジが単一ハブ「ノード」に集中しているわけではない(集中しているのは年代・政治・日付などの「ハブ的コミュニティ」— 前処理で対処可能)

### 危険サイン(観測されたもの)
- ⚠️ **out_ratio の絶対値はなお高い**(mixed で 0.28–0.53、geo で 0.37–0.63)。「内部>外部」が多数派だが、銀河間の辺も相当量ある → レイアウトは境界アンカー前提(§4.3)で設計する必要
- ⚠️ boundary_node_ratio ≈ 0.83–0.98 → 「境界ノードが小さい」理想形ではなく、境界は**要約表現**(隣接コミュニティ重心 + 集約重み)が必須
- ⚠️ geo 系はテーマ内で密に相互連結(行政階層・鉄道網・年表)しており、mixed 系より分割が難しい。**ドメインにより銀河の「鮮明さ」が違う**
- ⚠️ ハブ記事(年・日付・ISBN・郵便番号・地理座標系)が次数を支配 → 前処理なしの生グラフではコミュニティがハブに引きずられる
- ⚠️ エッジ総数が想定の 2 倍(142M 有向)→ 描画・配信設計の予算を再計算する必要

### 暫定判定: **B(条件付きで有望)**

条件とは:
1. レイアウト用グラフでは「smart 次数予算剪定 + 年代/日付/一覧/曖昧さ回避/テンプレ的ハブの特別扱い」を必須とする
2. 銀河間リンクはローカルジョブに全量渡さず、集約重み + アンカーに圧縮する(§4.3 の設計を堅持)
3. 階層は「細かい L1 → L2 集約」のボトムアップで構築する
4. 全グラフ規模での検証(次のフェーズ)をローカル 32GB で実施する(コードは本リポジトリで検証済み・そのまま拡張可能)

## 5. 再現手順

```bash
cd wikiuniverse
python3 -m wu.cli --base data download --files page,redirect,linktarget,pagelinks
python3 -m wu.cli --base data parse --dump-date 2026-09-02
python3 -m wu.cli --base data edges
python3 -m wu.cli --base data stats
python3 -m wu.cli --base data subset-bfs --seeds "東京都,大阪府,京都府,北海道,福岡県,愛知県,宮城県,広島県,新潟県,長野県,日本の地理,市町村" \
    --max-nodes 100000 --cap 60 --hops 4 --max-in-degree 10000 --name bfs_geo_100k
python3 -m wu.cli --base data analyze --subset bfs_geo_100k --out-dir results/bfs_geo_100k_raw \
    --resolutions 0.5,1.0,2.0 --engine igraph
```

計算時間実測(2vCPU/1GB RAM サンドボックス): download ~7 分、parse ~1.5 分(page 19s/linktarget 38s/redirect 9s)、edges 4.2 分、stats 45 秒、BFS サブセット抽出 ~1–2 分、Leiden(100k/5.1M エッジ)20–33 秒/run、解析全体 ~2 分。
→ **RAM 32GB のローカルなら全工程が数十分、全グラフ Leiden も視野**(142M エッジ ≈ igraph 構築 ~10GB、Leiden 本体は数十分〜数時間と推定)。

**診断**: モジュラリティ最適化の**解像度限界**(√2m ≈ 14,700 ノード未満を分解不能)と**ハブ支配**(平均次数 143)により、一括分割では銀河サイズ(数百〜数千)のコミュニティは得られない。これはフェーズ 1 の知見(ハブが構造を支配)のフルスケールでの再確認であり、**§4.1 の階層レイアウト=2 段階分割が「必要」であることが実証された**(方式の失敗ではない)。マクロ構造自体は強く健全(crossF 0.276、実質コミュニティの out_ratio p50 0.278、conductance p50 0.162)。

**対策(実装済み)**: `run_full_leiden.py subdivide` — 各マクロコミュニティの誘導部分グラフ内で Leiden を再帰実行し、全断片が max_galaxy 以下になるまで分割(解像度限界は部分グラフ規模が縮むため回避される)。→ `metrics/cluster/export --tag res1_sub` で 2 段階版の評価・銀河団(L2)生成・エクスポート。

**解釈**: 階層構造・サイズ分布・上位レベルの独立性は銀河方式の要件を満たす。一方、**生グラフ(テンプレート膨張、平均次数 143)の銀河レベル out_ratio 0.74 は「銀河を完全独立バッチとしてレイアウトする」ことの不可能さ**を示す — ただしこれは §4.3 が最初から想定していた状況であり、(a) レイアウト用グラフ(剪定/重み付け)、(b) 近傍アンカー制約付きローカルレイアウト、(c) 描画時のエッジバンドリング、の 3 点セットが「条件」として確定した。フェーズ 1 の 30k 実験(smart 剪定では crossF がほぼ不変)を踏まえると、**銀河独立性を根本改善する最大のレバーはテンプレート由来リンクの除去(XML ダンプから本文リンクのみ抽出)**と推定される(未検証、次の実験 E3)。

**解釈の改訂(E3 仮説の単純形は反証された)**:
1. **ナビボックスの半分は「銀河内セメント」だった**: navbox は主題ベース(「長野県の市町村」等)で同主題記事を密結合させていた。除去すると modularity 0.641→0.536 に低下
2. **本文リンクは「連想的」**: 記事本文は言及先(人物・地名・事件・概念)へ主題横断的に飛ぶ。銀河 oR は 0.738→0.850 へ悪化
3. **総合結論**: 「銀河サイズ(数百〜数千)で外部結合が弱い単位」は、生/剪定/本文の**どのリンク意味論でも存在しない**(oR 0.71–0.85)。一方マクロ構造は一貫して強い(生 crossF 0.276)。これは Wikipedia の編集行動の本質であり、方式の失敗ではない
4. **設計含意(判定 B の条件が確定)**:
   - 銀河 = **アンカー制約付きレイアウト単位**(自由バッチではない)— §4.3 設計の必須性が最終確定
   - 銀河の**意味付け(命名・色・UI グループ化)はカテゴリ情報から**行う候補 → E4(カテゴリ純度)で検証
   - リンク意味論の使い分け: レイアウト力 = 生/剪定グラフ、意味的接続の描画 = 本文グラフ
